Where to integrate

Guará exposes three integration seams. Selecting the correct one determines most of the work; selecting the wrong one leads to re-implementing assurance logic that already exists.

Integration seams, the interface each requires and the assurance each inherits.

SeamYou provideYou inheritEffort
Complex function A node publishing CfSetpoint Gateway clamps, geofence, DAA, monitors, arbitration, recovery Hours
Mission compiler A site model, and optionally a new intent verb Schema closure, deterministic checks, independent verification, the stop grammar Days
Monitor channel A FRETish requirement, and a verdict publisher Fail-closed gating, recovery ranking, latency accounting Days to weeks
Governing rule

A new flight operation gets its document before it gets code — one file per operation under docs/operations/, naming its checks, its channels, its recovery function and its evidence. The document is what a reviewer reads to determine whether the selected monitors cover the operation’s failure set.

A · Bounding an existing complex function

The complex function lives out of tree by design. The architecture makes no assumption about its implementation, its language, or its decision procedure. The interface is three numbers and a timestamp.

the entire contract
builtin_interfaces/Time stamp     # generation time on the CF clock
float32[3] velocity_ned_m_s       # commanded velocity, local NED frame
float32    yaw_ned_rad            # NaN leaves yaw uncontrolled

There is no mode field, no arm, no waypoint upload, no parameter write and no MAVLink. Your planner cannot request a mode change because the type has nowhere to put one.

  1. Publish on the CF topic, at your own rate

    The gateway measures freshness from reception on its own clock, not from your stamp — so a stall on your side is detected even if you keep stamping optimistically. Publish faster than the freshness window; the gateway does not care if you are irregular, only if you are late.

  2. Expect to be clamped, and read the counters

    Your velocity is clamped to gateway.max_*, non-finite values are rejected outright, and a velocity that the predictor says would breach the fence is blocked before it is forwarded. All four outcomes are counted in RtaState.

    watch what the boundary is doing to your planner
    ros2 topic echo /guara/rta_state --field cf_clamped
ros2 topic echo /guara/rta_state --field cf_rejected_guard
ros2 topic echo /guara/rta_event

    A planner that is constantly clamped is not being contained successfully — it is being contained repeatedly, which means it is wrong about the envelope it is flying in.

  3. Handle losing the aircraft

    When the arbiter leaves state CF, your setpoints stop at the gateway. They are not queued and they are not applied late — a setpoint stamped before the most recent return instant is discarded. Subscribe to RtaState and stop planning into a future you no longer control.

  4. Earn the aircraft back

    The return is not automatic and not fast. The clear condition must hold continuously for the dwell time, the minimum dwell in recovery must elapse, the switch budget must not be exhausted — and the shadow check must agree that what you are currently proposing is itself safe. A planner that keeps re-proposing the motion that got it cut off will never come back, and after N_max switches the recovery latches permanently.

  5. Test it against the nasty scenarios

    Fourteen scenarios ship, and the useful ones are the hostile ones.

    shell
    ./scripts/sitl_run.sh --scenario gf_straight_concave --seed 42 --headless
./scripts/sitl_run.sh --scenario kill_arbiter_in_cf   --seed 42 --headless
./scripts/sitl_run.sh --scenario stale_local_position --seed 42 --headless
./scripts/sitl_run.sh --scenario pilot_override       --seed 42 --headless

# the one that proves the boundary did something: same plan, same seed, RTA on and off
./scripts/sitl_pair.sh --scenario gf_straight_concave --seed 42

B · Embedding a language model

Three decisions shape this path, and each of them is a restriction on what the model is permitted to produce.

The model never emits setpoints

No velocities, no MAVLink, no code, no coordinates. It emits a typed Mission Intent over a closed vocabulary, and a deterministic compiler turns that into a plan.

The stop path skips the model

abort, land_now and return_home are exact-match grammar plus a physical button. A stop must not depend on a model being reachable, correct, or fast.

Geography is not the model’s to invent

The site model is the only source of geography. The model names fields and points that exist there and nothing else, because it has no metric grounding.

The whole pipeline, with the trust position of each stage

1Stop grammarmodel-free
2Model → intentuntrusted
3Schema validationclosed vocab
4Compilerdeterministic
5Independent verifyre-derived
6Plan executorbounded
7Gatewayclamped
8Arbiter → PX4assured

Stage 1 runs first, on the raw transcription. If it matches, no request is made to anything. The grammar is biased toward over-triggering — a false stop costs a flight, a missed stop can cost an aircraft — and the evaluation harness reports how many cases were resolved that way rather than hiding it.

Stage 2: the only artefact a model may produce

The schema is closed (additionalProperties: false), and geographic literals are absent by design. There is no field for a latitude, so there is no prompt that produces one.

mission/schema/mission_intent.schema.json — the vocabulary
"intent":  ["survey", "inspect_point", "return_home", "land_now", "status", "abort"]
"field_id": pattern ^[a-z0-9][a-z0-9-]*$   // must exist in the site model
"poi_id":   pattern ^[a-z0-9][a-z0-9-]*$   // a named point, for inspect_point
"sensor":  ["rgb", "multispectral", "thermal"]
"gsd_cm":   number, 0 < x <= 100
"overlap":  { "front": [0,1), "side": [0,1) }
"altitude_agl_m": number or null    // null means the compiler derives it
"deliver": ["orthomosaic", "ndvi", "ndre", "thermal_map", "photos", "plant_count"]
"utterance_hash": "sha256:<64 hex>"  // audit link to the recorded command

utterance_hash is the field people skip and should not. It binds a plan to the recorded utterance that produced it, so a post-incident question — what was actually said? — has an answer that does not depend on the model remembering.

Three named failures, a non-zero exit status, and a refusal an operator can act on. Notice that the checks that passed are printed too — a refusal that only shows failures teaches you nothing about how close the rest of the plan was.

Rationale for stage 5

The compiler both builds a plan and declares it flyable. Asking the same code whether its own output is safe is a tautology. So verify.py re-derives the constraints by a different route: it reads the serialised waypoints, re-projects them, tests containment against the fence and the field polygon directly — not the eroded coverage box the planner used — and recomputes the energy from the waypoint list rather than trusting the plan’s own figure. It shares only the projection and the point-in-polygon primitive with the compiler. A disagreement between the two is a defect in one of them, which is the point.

Pointing it at your own site

The site model is the only source of geography, and it is the file you write. The keep-in fence in it is the same polygon the arbiter loads and PX4 loads, hashed into every compiled plan — one file, not three that drift.

mission/site/demo_farm.yaml — the shape to copy
site_id: demo-farm

origin:              # local frame reference; equals the SITL home point
  lat: -22.0087
  lon: -47.8909
  alt_amsl_m: 850.0

pilot:               # remote pilot standing position, for the VLOS check
  north_m: 0.0
  east_m: 0.0

geofence:            # keep-in fence; the same polygon PX4 and the arbiter load
  polygon_lat_lon_deg:
    - [-22.00923959, -47.89245202]
    - [-22.00636176, -47.89245199]
    - [-22.00636176, -47.88934801]
    - [-22.00923959, -47.88934798]
  alt_min_m: -1.0
  alt_max_m: 130.0

limits:
  max_altitude_agl_m: 120.0    # regulatory ceiling
  min_altitude_agl_m: 5.0      # lowest altitude the compiler will plan
  vlos_radius_m: 500.0         # visual line of sight radius from the pilot
  fence_margin_m: 5.0          # planning margin kept inside the fence
compile against it
python3 -m mission.compiler --intent my_intent.json --site mission/site/my_farm.yaml
python3 -m mission.compiler --intent my_intent.json --json > plan.json
Status of the values in the reference site model

Every limit and every battery number in demo_farm.yaml is labelled in the file itself as a hypothesis or a parameter to be determined. None is a measurement. The regulatory ceiling in particular is marked for review against RBAC 100. Copy the shape; measure your own values.

Choosing the model — and why it barely matters

A provider is a text channel: prompt in, text out. It never sees the site model, never sees a plan, and never learns what the expected answer was. Adding one cannot change a result, which is precisely why the comparison is meaningful.

Model providers shipped with the evaluation harness.

ProviderNeedsUse it for
mockNothing — no key, no networkMaking the harness itself testable, and CI
ollamaA local open-weight modelThe intended deployment: no key, no account, no cloud
openai-compatA base URLvLLM, llama.cpp, LM Studio, OpenRouter, OpenAI — selected by URL

run the labelled corpus against a model
# the intended deployment: a local open-weight model, no key and no account
ollama pull llama3.1:8b
python3 scripts/llm/eval.py --provider ollama --model llama3.1:8b --repeats 3

# any OpenAI-compatible server, selected by base URL
export GUARA_OPENAI_BASE_URL=http://localhost:8000/v1
python3 scripts/llm/eval.py --provider openai-compat --model <id>

# just the adversarial class
python3 scripts/llm/eval.py --provider mock --only-class adversarial

Every exchange is written to results/{run_id}/exchanges/ before it is scored, so every reported rate can be recomputed from the run directory alone. The corpus ships nominal, ambiguous and adversarial classes; the adversarial one includes utterances that try to talk the system out of its own safety rules.

C · Adding a flight operation

An operation is a document first. Copy an existing one — survey is the reference — and fill in the six things a reviewer needs before any code is worth writing.

Required sections of a flight-operation document.

SectionWhat it must answer
Intent verb & capability classWhich closed-vocabulary verb, and which risk class it falls in
What the operator asks forThe real utterances, in every shipped language, and the intent they produce
Words to motionThe stage table, with the trust position of each stage stated
What refuses it before flightEvery named compiler check, each with a unit test that makes it the only failing check
What watches it in flightWhich channels are enabled, what signal each produces, and which recovery it requests
EvidenceThe run directories that show it working, or an explicit statement that there are none yet

Capability classes, and why three of them will refuse to load

Operations are grouped by what they can physically do wrong, and a capability pack loads only when every monitor it requires exists and passes its acceptance criteria.

S · sense

available

Survey, inspection, mapping, livestock, forestry. No physical interaction with the ground.

D · dispense

gated

Spraying, spreading, biological release. Refuses to load until its monitors exist.

T · transport

gated

Carrying a load changes the failure set and the airframe tier. Also gated.

C · cooperate

gated

SAR support, multi-vehicle. Gated on monitors that do not exist yet.

Permanently out of scope

Weapons and any payload intended to harm; target selection; tracking or identification of specific people for enforcement or harassment; covert surveillance; interference with other aircraft; and defeating geofences, remote ID or failsafes. A capability pack implementing any of these will not be accepted, and this is a project rule, not a configuration option.

Then write the test that fails first

Every safety function has a test that fails before the implementation exists. For a compiler check specifically, the bar is sharper: the test must construct an intent where your new check is the only failing one, so a later refactor cannot make it pass by accident through some other constraint.

shell
python3 -m pytest scripts/tests -q                   # compiler, corpus, executor, keep-out
./scripts/dev.sh colcon test --packages-select guara_rta guara_geofence guara_monitors
python3 scripts/check_links.py                       # every relative document link resolves

D · The switching core in orbit

Maturity of this path

The space thread is specified, not implemented. There is a closed intent schema, a tested attitude keep-out predictor, and a demo-satellite vehicle model. There is no host, no simulator, and no safe mode. If you are looking for something to fly next quarter, this is not it. If you are looking for the place where a contribution changes the shape of the project, this is exactly it.

The intent vocabulary is closed the same way the air one is, and the verbs are different because the operations are:

space/schema/space_intent.schema.json
"intent": ["slew", "point_hold", "safe_mode", "status", "abort"]
"boresight_id"   // a protected instrument axis from the vehicle model
"target_id"      // a named target from the vehicle model
"hold_s"
"utterance_hash"

Three differences you must design around before writing any of it:

  • The recovery function does not exist. F´ detects but does not recover. A safe mode has to be written, and it has no flight heritage in this codebase — the single largest risk in the thread.
  • The recovery is latched. There is no dwell-time return in orbit. Once the arbiter takes the spacecraft, only a ground command gives it back.
  • There is no detect-and-avoid, and there never will be. Conjunction assessment is a ground-based probabilistic process; a DAIDALUS port would be overreach. The channels are attitude keep-out, power margin, momentum, inputs and requirements.
what exists today, and how to check it
./scripts/dev.sh python3 scripts/check_ac.py AC-47    # attitude keep-out predictor
python3 -m pytest scripts/tests -q                    # includes the keep-out tests

Safety profiles and declared omissions

Guará runs under a profile — sitl or flight — and the difference is not a log level. Under the flight profile, an undeclared omission makes the process refuse to start.

You may turn a protection off. You may not turn it off silently. The omission is declared in configuration, echoed in RtaState.accepted_omissions, and recorded in the run directory, so a result produced with the DAA channel disabled cannot later be cited as though it were not.

config/rta_params_flight.yaml is the one to read before flying
config/rta_params.yaml         # SITL defaults
config/rta_params_flight.yaml  # the flight profile: stricter, and refuses undeclared omissions

Every run copies its parameters into results/{run_id}/config.yaml, alongside the scenario hash, the seed, the Guará SHA, the PX4 build commit, the pinned third-party commits, and the PX4 parameters read back from the vehicle. That last one is what makes a number re-derivable rather than merely reported.

E · Preconditions for operation on hardware

No result in this project is a claim about real flight, and this is stated before any result. If you intend to fly it anyway, these are the things that are known to be missing — addressing them is the minimum precondition.

  • Authenticate the DDS transport. Right now a hostile node on the domain can publish setpoints, and that is an accepted limitation of this phase, not a solved problem.
  • Re-measure δ_lat on your companion computer and your link. The 61 ms figure is a specific machine running SIH SITL, and it is optimistic by construction.
  • Re-derive τ_gf and τ_daa from that measurement. A trigger threshold shorter than your own latency is a threshold that does nothing.
  • Fix the clock alignment before citing any cross-process number. The reference setup is off by seconds.
  • Replace every hypothesis value in the site model with a measured one — especially the battery model, which is what the energy refusal depends on.
  • Confirm the arbiter’s failure modes are acceptable to you: with an internal recovery mode active its death is invisible to PX4, and it cannot re-register in flight.
  • Leave the PX4 failsafes and geofence enabled. Guará is not the last line of defence and is not built to be.
  • Check your own regulatory position. Nothing here demonstrates compliance with F3269, DO-365 or RBAC 100.
