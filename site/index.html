Runtime assurance · ASTM F3269 · Apache-2.0

A measured safety boundary for autonomous and LLM-embodied flight

The complex function proposes, the arbiter disposes, the autopilot recovers, the human commands. Authority is ordered, and the order does not invert.

Guará is an open, measured safety boundary between an unassured complex function — a language model, a neural policy or a classical planner — and a real vehicle. The complex function never reaches the actuators. It proposes, through a gateway that clamps what it may ask for, while runtime monitors evaluate the physical state. When the next seconds are predicted unsafe, authority is withdrawn and the vehicle is handed to the platform’s own assured recovery mode.

In the air this runs today on PX4 and ROS 2, and the switch is measured, not asserted. In orbit the same core is specified against F´.

Why this exists

The gap

Talking to a drone is a crowded field — ChatGPT for Robotics, TypeFly, EchoPilot, MAVLinkMCP, AerialClaw. Survey them and the safety story is uniform: prompt engineering, tool restriction, and a human with a kill switch. All three live inside or beside the model, and all three fail together.

RoboPAIR reports a 100% jailbreak rate against three LLM-controlled robots. A guardrail constrains the planner. Guará constrains the aircraft — the one layer a jailbreak has no words for, because it does not read them.

The parts to build that boundary already exist and are NASA-maintained: FRET for requirements, Ogma to generate monitors, Copilot for verified C99, DAIDALUS for DO-365 detect-and-avoid. None of them reaches the dominant open autopilot, and nothing between them closes the loop from a property is about to break to the aircraft changes mode.

G2

Ogma generates monitors for cFS, ROS 2, F´ and standalone — no PX4 target, though PX4’s uXRCE-DDS bridge already exposes uORB as ROS 2 messages.

G3

PX4’s external-mode fallback fires only when the mode dies. Nothing switches mode because a safety property is about to break.

G4

The monitoring literature (Volocopter/DLR, CAV 2024; Platum, NFM 2026) explicitly leaves “trigger the contingency automatically” as future work.

G1

NASA’s integrated safe-drone stack, ICAROUS, stopped at V-2.2.6 in January 2022, on cFS with an external autopilot.

The idea in one picture

Ordering of authority

The complex function proposes, the arbiter disposes, PX4 falls back, the human commands. Each box below is a real package in the repository, and each arrow is a real topic.

Untrusted means bounded

Not merely unprivileged. The gateway states exactly what it accepts: freshness on the receiver’s clock, envelope clamps, and a shadow check of the proposed velocity against the geofence predictor before forwarding it.

Asymmetry

Hysteresis and dwell time delay only the return to the complex function. Nothing intentionally delays the switch away from it. Leaving is immediate; coming back must be earned.

Fail closed, degrade loudly

An enabled channel that goes silent is treated as a violation. An undeclared omission makes the flight safety profile refuse to start at all.

Try it now

Verification without a container

You do not need ROS 2, a PX4 build, a container, a GPU, a model or an API key to see the boundary work. One install and one command. guara doctor is the workstation preflight: it prints the resolved pins, the platform and the tier it reached, so a setup that cannot work says so before a run fails halfway.

The refusal case is the load-bearing one: an intent that is well-formed, schema-valid and entirely plausible is rejected by named, deterministic checks before anything flies. It asks for 40 cm/px, which would put the aircraft above the regulatory ceiling with not enough battery to finish.

Turning an utterance into an intent is the untrusted step, and it is the only step a model is allowed to take.

Compiler checks
shell
git clone https://github.com/aton-of-data/guara-llm-embodied-flight
cd guara-llm-embodied-flight
pip install -e .
guara doctor

# an intent inside the envelope -> a flyable plan (exit 0)
guara compile --intent mission/intents/survey_north_3.json

# the same survey at 40 cm/px -> refused, with the checks named (exit 2)
guara compile --intent mission/intents/survey_north_3_out_of_envelope.json
# refused (checks): gsd_bounds, altitude_ceiling, energy

# the stop path, which never reaches a model at all
guara compile --stop "land now"     # -> land_now
guara compile --stop "pouse agora"  # -> land_now

The last two lines are the same grammar in two languages. abort, land_now and return_home are exact-match patterns plus a physical button, mapped straight to platform modes. A stop must never depend on a model being reachable, correct, or fast.

What the project says about its own numbers

Cross-process DDS latency is not publishable. Because the PX4 and ROS clocks differ by seconds here, the mixed-clock stage L1 is recorded but excluded from δ_lat, and AC-19 gates any cross-process number until alignment is under 10 ms. δ_lat is optimistic by construction: the latency_hold scenario injects the monitor verdict, so Copilot processing time is zero on that path.

The acceptance-criteria tracker is also explicit about its own history: an internal review on 2026-09-11 invalidated one false PASS and eleven rows produced by a checker that had stopped running. The latency batch above was discarded and re-measured from scratch on the corrected build. Full evidence, criteria and re-run commands →

One switching core, two hosts

Domains: air and space

The space thread is a rewrite of the signals, not a port. An orbiting body cannot stop, so the braking model behind the air geofence does not transfer, and detect-and-avoid has no orbital analogue that belongs onboard.

There will never be a DAA channel in orbit. Conjunction assessment is a ground-based probabilistic process; porting DAIDALUS there would be overreach.

Rule O

No F´ or space work starts before the PX4 latency and batch results are complete. That rule is why the space thread today is one carefully tested geometric predictor rather than a half-finished port.

Read this before citing anything

Limits

This is a research prototype, not a product and not a certification. Its claims are limited to what an executed command supports. The limits below are the ones most often overclaimed by projects in this space, so they are stated first rather than last.

Limits and failure modes
  • It is not certification. No compliance with F3269, DO-365 or RBAC 100 is shown.
  • It does not guarantee collision avoidance. The v1 DAA recovery is Hold, and stopping does not move you away from a converging intruder.
  • It does not survive all of its own failures. With an internal recovery mode active, the arbiter’s death is invisible to PX4, and it cannot re-register in flight.
  • It does not protect against spoofed inputs. DDS is unauthenticated in this phase.
  • It cannot detect a wrong requirement. A bad FRETish formalisation passes silently.
  • It runs outside the FMU, without the autopilot’s real-time guarantees. Decision time is measured, not proven — there is no WCET analysis.
  • SITL does not transfer. No result here is a claim about real flight.
  • It does not make a language model correct. A mission-level mistake inside the safe envelope — wrong field, wrong dose, wrong photograph — is invisible to everything in this repository.

Where you come in

Open work

These are not “good first issue” placeholders. Each one blocks a named risk or a research question, and each is a self-contained contribution someone with the right background can finish.

Unblock formal verification

A working Haskell / LLVM / z3 environment for CopilotVerifier — the generated monitor C99 is currently trusted rather than proved.

risk R-11 · blocks RQ4

Well-clear thresholds for small UAS

DO-365B thresholds are written for larger aircraft. Sourced, citable values for small multirotors would replace a parameter that is currently a hypothesis.

risk R-5

Traffic injection in PX4 SITL

The DAA path has never faced a real converging intruder in simulation, because there is no injection path. Building one turns an untested branch into a measured one.

risk R-7

Authenticate the transport

An SROS2 profile for the complex-function and FMU topics. Until it exists, a hostile node on the DDS domain is an accepted limitation.

failure mode FM-12

Orbital dynamics for the arbiter

A Basilisk ↔ ROS 2 setup that lets the existing decision core face real orbital dynamics instead of an analytic predictor.

AC-48 · space thread

Review the safe mode

Someone who has actually flown a spacecraft safe mode, reading the specification for what it gets wrong. This is the risk a reviewer should attack first.

risk RS-1

Write the core from the spec alone

A second implementation of the decision core, by a path independent of the existing one, to find out what the specification fails to say. No hardware, no container, no ROS — and the C ABI stays provisional until it exists.

gap G-K6

Attack the orbital boundary

The adversarial corpus is air-only, so the orbital jailbreak criterion has nothing to run. A slew whose endpoints are both legal and whose path crosses a keep-out is the shape of the missing case.

gap G-Z9

Every item above names a row of the gap register — the full list of what this project knows it is missing, each with the milestone that owns it. It is on the roadmap page.

Fund the parts that cost money

Guará is Apache-2.0 and independent. The work that money unblocks is specific and physical: hardware-in-the-loop benches, a reference airframe for the first real flight campaign, licensed standards access (the ASTM F3269 text is not available to this project), and the review time of people who have certified avionics before.

Sponsorship, grants and institutional collaboration: dornfeld.in@gmail.com.

Use it, and say what broke

The most valuable early contribution is a report from a setup that is not the author’s: a different airframe, a different distro, a different model behind the intent compiler. The evaluation harness ships four providers, including a mock that needs no key and no network.
