1 · Where the work is

A milestone is not complete without an executed command and an excerpt of its output, and an acceptance criterion is PASS only on the same terms. Code existing is not a criterion being met, which is why several rows below say in progress while their code is already in the tree.

Milestone state by thread. The authority for every cell is docs/milestones/STATUS.md in the repository; this table restates it and does not extend it.

What this page is not

It is not a schedule and carries no dates. A single-author research project that published a delivery date would be publishing a guess. What it does carry is an order, and the rules below are what fix that order.

2 · The four ordering rules

Each rule exists because the cheapest mistake available to this project is to let an interesting thread outrun the evidence that makes it meaningful.

The rules that decide what may start when, and the failure each one prevents.

RuleSaysPrevents
O — scope protectionNo F´ or space work begins before the PX4 latency and batch results are complete.A half-ported second host standing in for results the first host never produced. This rule is why the space thread today is one carefully tested geometric predictor.
D — deliveryNothing is published whose conformance report is missing or failing, and no published artifact claims safety of itself. No release without an SBOM, a provenance attestation and a licence-boundary check.An installable artifact that people fly, carrying an implied assurance nobody generated.
H — hardware gateSITL → hardware-in-the-loop → bench → tether → low-altitude → operational, each step's evidence bundle a precondition of the next. No flight with a model in the loop before transport authentication passes on the same configuration that flies.The step from simulator to aircraft being taken in one jump, which is how this class of project hurts someone.
T — trust boundaryNo milestone gives a language model a shorter path to an actuator than intent → deterministic compiler → validated plan → trusted executor → gateway → arbiter → platform recovery function.Capability creep at the boundary: the model gaining reach because a feature was convenient.

3 · Tracks and sequence

Four tracks run past the current work. The kernel track feeds both domains, which is the whole architectural claim: one switching core, two hosts, one conformance kit deciding whether they agree.

                              │                      │

The asymmetry between the domains

On PX4 the recovery function was free: Hold, RTL and Land are assured, pre-existing, pilot-familiar modes, and the contribution is only the switching logic. F´ ships no safe mode at all — a search of the pinned clone returns nothing — so in orbit the project must supply both halves, and the recovery half is new safety-critical code with no flight heritage. That is risk RS-1, and it is the one a reviewer should attack first.

4 · The gap register

Every row is a real absence, not an aspiration, and every row has exactly one owning milestone. The full register with its wording and its traceability table is docs/PLAN-M17-M28.md §1; what follows is the same content grouped by track.

G-S · setup and reproducibility

Gaps in making the project run identically on a machine that is not the author's.

#GapOwner
G-S1Python dependencies were floors, not pins: two machines resolved two environmentsM17
G-S2Pins duplicated between requirements files and the Dockerfile, with nothing detecting driftM17
G-S3Nothing was installable, so the smallest path only worked from a cloneM17, M20
G-S4The dev image is built locally and amd64-only; the registry publish is manual, so there is no reliable pull path and none at all for arm64M17
G-S5No workstation preflight: nothing checked architecture, Docker, disk, memory, clock skew or pinned clone commits before a run failed halfwayM17
G-S6No offline path: fetching sources and building the image both needed the networkM17
G-S7Continuous integration tested only the Python layer, so the arbiter could break silentlyM17
G-S8ROS 2 Humble reaches end of life in May 2027, inside this plan's horizon, with no migration scheduledM20

G-K · the kernel and its delivery

Gaps between a switching core that works in this repository and one a third party can consume and check.

#GapOwner
G-K1The core was ROS-free in its code but ROS-packaged in its build, so no non-ROS host could consume itM18
G-K2No C ABI, no versioned interface, no caller-supplied storage — the shapes a flight-software integrator expectsM18
G-K3No semantic version, no ABI gate, no behavioural-compatibility gate between releasesM18, M20
G-K4No worst-case evidence: bounded work per tick is asserted by construction and by a no-allocation test, never measured on a targetM18, M22
G-K5No conformance vectors an integrator could run; host equivalence was an internal claim with no shippable artifactM19
G-K6No independent implementation had read the specification, so the specification's ambiguities were unknownM19
G-K7No binary distribution on any channel: no packages, no wheel, no F´ library, no multi-arch image, no SBOM, no provenanceM20
G-K8Runtime configuration was loaded without a schema check or a hash recorded against the running coreM18, M23

G-M · monitors, requirements and the specification

The signals the whole architecture switches on, and the document two hosts have to agree through. Both rows are new as of 2026-09-13.

#GapOwner
G-M1No standing check that a deployed monitor is non-vacuous — although the defect has already occurred once, with a requirement reporting a violation in every one of 1728 verdicts including on the ground, and a checker that accepted it. That requirement and that checker were fixed; the class was notM2
G-M2The specification does not state semantics the decision core has: the recovery rank never falls once escalated, and a return to the complex function is possible only from the mildest recovery. Both behaviours are safe; neither is written down, so an independent implementation can get them wrongM19

G-H · air, on real hardware

Everything between a measured simulation and a flight. Three rows moved to the air thread on 2026-09-13 because none of them needs hardware.

#GapOwner
G-H1No hardware-in-the-loop stage at all: the step from simulation to flight is a cliffM21
G-H2Every latency number is x86 simulation; nothing measured on an arm companion under a general-purpose kernelM21, M22
G-H3No companion target: no arm64 image, no boot service, no scheduling policy, no isolation between the arbiter and the complex functionM22
G-H4No dead-man between companion and flight controller on real hardware; the autopilot's offboard-loss failsafe is neither configured nor tested as a criterionM22
G-H5No black box: no single bundle correlating the autopilot log, the recorded topics and the arbiter's events on one timebase, and no measured clock offset between themM23
G-H6No arming gate: nothing refuses to fly when the loaded geofence, parameters, monitor build or core version differ from the declared setM23
G-H7The operator cannot see the arbiter: no ground-station annunciation of a switch or its causeM23
G-H8The override matrix — radio loss, ground-station loss, companion loss, kill switch, pilot mode change, low battery — is untested on hardwareM23
G-H9No operational safety dossier: no concept of operations, no system-level hazard and failure-mode analysis, no operational-risk assessment mapping, no regulatory position for Brazil or Europe, and no explicit map of which certification objectives are not claimedM24
G-H10The hardware run has no evidence contract: aircraft, pilot, site, weather, battery, waiver and firmware hash are required fields nowhereM23, M25
G-H11Transport authentication is open, and it is a hard precondition for any model-driven complex function on a real vehicleM9b
G-H12No model-side runtime discipline: no request budget, no hard timeout, no watchdog on the model process, no defined degraded mode when it is unreachableM9b
G-H13The adversarial corpus was written by the author of the compiler it attacks, and has never been externally reviewed or coverage-measuredM9b

G-Z · space

The orbital domain. Five rows are new as of 2026-09-13, four of which need no hardware and no F´ host.

#GapOwner
G-Z1The F´ host is unextracted and the safe mode unwritten — everything downstream is blocked on themM13/M14, M26
G-Z2No cross-compilation and no processor-in-the-loop: nothing has run on an onboard-computer-class boardM26
G-Z3“Released only by ground command” is a sentence, not an interface: no authenticated telecommand path and no rejection test for a non-ground releaseM27
G-Z4No standard packet-services framing: the channels and events are not expressed as on-board monitoring, events or event-action definitions an operator would recogniseM27
G-Z5No time system declared, and clock drift unbudgetedM27
G-Z6No orbital simulator is pinned, so the orbital criterion has nothing to run againstM27
G-Z7Only the analytic keep-out channel exists; power margin, momentum, input validity and requirements have no implementationM26
G-Z8No map of which space software-engineering objectives are not claimed, the sibling of G-H9M27
G-Z9The adversarial corpus is air-only — fields, spraying, ground sample distance, ceiling, geofence — so the orbital jailbreak criterion has nothing to run: every air case dies at the space schema, for the wrong reason, and the run looks like a passM16
G-Z10No authenticated origin for a space intent or a sequence. G-Z3 covers only the safe-mode release; the command path reaching the sequencer is unconstrained, and a default F´ uplink authenticates nothingM27
G-Z11The air gateway's rules had no space instantiation: no freshness source, no envelope clamp on commanded rates, no shadow keep-out check on a proposed slew. ADR 0015 now decides it; the implementation is openM26
G-Z12The space decision rules are not published as conformance vectors, so an F´ port would be trusted to match the reference rather than checked against itM19
G-Z13Whether safe-mode entry can itself violate a keep-out is unmeasured. A star tracker's keep-out cone is declared around the body that blinds it, so a direct slew to a sun-pointing recovery attitude may sweep the very cone it must avoidM14
Three criteria expected to find something

Ten ground-side acceptance criteria were added on 2026-09-13, none of which needs hardware, a host, a simulator or a network. Three of them are predictions of a defect rather than confirmations of a design: that the specified safe mode is unsafe for a measurable fraction of initial attitudes (G-Z13); that at least one deployed monitor's verdict never changes (G-M1); and that the independently written reference implementation disagrees with the C core on a rule the specification never stated (G-M2). All three are cheap to test now and expensive to discover later.

5 · Risk families

Risks are numbered in four families across four documents. A gap is a known absence; a risk is something that could invalidate work already done.

The four families, what each covers, and the document that defines it.

FamilyCoversDefined in

RP-1…RP-3The LLM-embodiment programme: who wrote the corpus, what its size boundsdocs/PLAN-M8-M16.md §6
RS-1…RS-6The space thread: the safe mode with no heritage, the pre-release sequencer, simulator fidelitydocs/research/SPACE-AUTONOMY.md §8
RH-1…RH-9Delivery and hardware: end-of-life distributions, publishing posture, vendor capture, measured-versus-proven timingdocs/PLAN-M17-M28.md §7
The two that cost most if ignored

RS-1: the orbital recovery function has no flight heritage because it does not exist yet. RH-9: measuring on a general-purpose kernel yields distributions, not bounds — every timing figure this project publishes is a worst observed value, and a real bound would need a worst-case-execution-time tool and a real-time operating system, neither of which is in scope. Anyone reading a measured p99 as a guarantee is reading it wrongly, and that sentence travels inside the artifacts rather than only on this page.

6 · What a contributor can take

The items below are bounded, each blocks a numbered gap or risk, and none of them requires hardware this project does not have. The full list, with what each one asks of you, is on the contribution page.

  • Write the switching core from the specification alone. A second implementation, by a path independent of the existing one, to find out what the specification fails to say. No hardware, no container, no ROS. It is the single item that would most improve the specification, and the C ABI stays provisional until it exists (G-K6).
  • A space adversarial corpus. A file of utterances that attack the orbital boundary rather than the air one: a slew whose endpoints are both legal and whose path crosses a keep-out, a request to release the safe-mode latch, a sequence whose members are individually valid and whose aggregate exhausts momentum (G-Z9).
  • Measure the safe-mode entry manoeuvre. Sweep initial attitudes and count how many direct slews to the survivable attitude cross a declared keep-out cone. Needs the analytic predictor that already exists and nothing else (G-Z13).
  • First timing numbers that are not x86. Anyone with a small arm board can produce the first on-target measurements this project has (G-K4, G-H2).
  • Port the packages ahead of the distribution's end of life in May 2027 (G-S8, RH-1).
  • Review the safe-mode specification — ideally someone who has flown a spacecraft safe mode, reading it for what it gets wrong (RS-1).
And the most valuable report of all

A run from a setup that is not the author's: a different airframe, a different distribution, a different model behind the intent compiler — and a description of what broke. The evaluation harness ships a provider that needs no key and no network, so reproducing the pipeline costs nothing but time.
