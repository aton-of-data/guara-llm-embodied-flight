## 1. Critical — evidence invalid

### C-1 AC-15c is a false PASS; FM-3 was not reproduced
- PX4 SITL sets `param set-default COM_MODE_ARM_CHK 1` (`third_party/PX4-Autopilot/ROMFS/px4fmu_common/init.d-posix/px4-rc.simulator:8`).
  Every Guará SITL run therefore allows registration while armed. That contradicts ADR 0001 rule 6
  and the default-0 assumption in GROUNDING 2.7/A.16.
- `Mode '…' already registered` is printed by `Modes::addExternalMode` (`ModeManagement.cpp:137`)
  on the accept path: PX4 picks a new index and continues. The rejection path prints
  `Not accepting registration requests while armed` (`ModeManagement.cpp:378`).
- Run `20260911T190155Z_restart_arbiter_armed_s42`: `guara_rta_node_restart.log` line 1 reads
  `registered 'Guara CF Gateway' (executor id 2, nav_state 24)`. px4.log shows the warning between
  `Takeoff detected` and `Disarmed by landing`. **The in-flight re-registration succeeded.**
- The first attempt (`20260911T185951Z`) failed while waiting for the correct rejection string.
  After that, the scenario (`scenarios/restart_arbiter_armed.yaml:24`) and the checker
  (`scripts/check_ac.py:221`) were changed to match `already registered`.
- Action: set STATUS to FAIL. Force `COM_MODE_ARM_CHK 0` in the runner, record it in
  `config.yaml`, and make the run contract check it. Make the checker require the rejection string
  and a restart log with no `registered`. Re-run AC-15, AC-15b, AC-16 and AC-16b too, because they
  ran with a non-default parameter. Correct the M3 report text.

|---|---|---|---|---|
| H-1 | CF freshness uses the **CF-supplied** stamp | `gateway_logic.hpp:57` | An untrusted CF stamps one setpoint in the future and dies. `t − stamp ≤ timeout` stays true, so that velocity is forwarded indefinitely and the CF-liveness timeout is defeated. | Measure age from reception on the gateway clock. | H-2 | No envelope on CF setpoints | `gateway_logic.hpp` `onCfSetpoint` | Any finite velocity or yaw is forwarded. The geofence braking model (`d_stop = v²/2a`) assumes speeds inside the envelope. ## 4. Design issues (not AC failures)

- **Return ignores the CF's intent** (root cause of the AC-9 oscillation). A stopped vehicle has
  `speed < v_min` ⇒ `T_gf=+inf` ⇒ clear (`predictor.cpp:225`), so T5 hands control back to a CF
  that immediately flies at the fence again. Evaluate `T_gf` on the CF's **proposed** velocity
  (shadow check) before T5 and before each forwarded setpoint.
- **Lateral uncertainty is ignored.** `k_sigma·eph` is subtracted only along the velocity ray. Flying
  parallel to a wall, or hovering, within `k_sigma·eph` of the boundary never triggers.
- **Latch bypass:** T1 resets the switch history (`decision_core.cpp:149`). Re-entering the owned mode
  clears `N_max`. This matters once an agent has mode-switch tools.
- **Mode effect not confirmed:** an ACK is attributed to whatever request is pending, and `nav_state_`
  is stored but unused. Confirm the effective `nav_state` and escalate on timeout.
- **Actuation-failure latch leaves the vehicle hovering in the owned mode.** Prefer failing the owned
  mode's arming check so PX4's own fallback chain takes over.
- **Untested glue:** the monitor table, action mapping, channel gating, ACK handling and failure path
  in `arbiter_node.cpp` have no unit tests, and H-3…H-6 all live there. Extract them into pure
  classes with tests that fail first (CLAUDE.md).
- **Hygiene:** three Ogma-derived template sources (Apache-2.0) lack SPDX and Ogma notice lines.
  `results/` is gitignored, so evidence cannot be reviewed off this machine; commit `metrics.json`
  summaries or archive run bundles.

## 5. LLM / autonomy readiness (M8–M12)

`docs/research/LLM-EMBODIMENT.md` §4–5 is the right architecture: the LLM emits a closed Mission
Intent, a deterministic compiler checks the plan, the RTA bounds the flight, PX4 falls back, and stop
commands bypass the LLM. Before any LLM (API or embedded) drives a CF, close these gaps:

1. H-1, H-2, H-3…H-5 and the latch bypass. An adversarial CF will find each of these first.
2. The LLM stays out of the setpoint loop. API latency is seconds; the gateway timeout is 0.5 s. A
   trusted plan executor tracks setpoints, and the LLM only updates the plan.
3. Shadow-check proposed commands (§4) so an aggressive or hallucinating planner is filtered before
   it moves the vehicle, not only after.
4. Treat LLM or link unavailability as a monitored input that pauses the *mission*, not the vehicle's
   safety layer. The offline embedded model is a planner fallback only.
5. SROS2 on `/guara/cf/*` and `fmu/in/*` (FM-12) before any networked agent.
6. RQ6b jailbreak corpus against the compiler, and RQ5 against the gateway, including future stamps,
   NaN/extreme values and mode-tool abuse.
