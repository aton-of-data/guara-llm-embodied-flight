# ADR 0002 — Monitors on the companion (phase 1) vs. in the FMU (phase 2)

- Status: Proposed (P1, 2026-09-11)
- Related: SPEC §2, §4, §7 item 7; ADR 0001

## Context

Copilot monitors can run (a) as a ROS 2 node generated by Ogma on the
companion/SITL or (b) as C99 code inside a PX4 module.

- Ogma v1.15.0 generates a ROS 2 application with a customizable template; the monitor
  C code is inserted manually (`monitor.h/.c`) [G 4.3-4.6].
- The default template has QoS incompatible with PX4 [G 4.5].
- Ogma v1.15.0 has cFS, ROS and F Prime backends [G 4.3]; **no PX4 backend**
  verified. Integration of Copilot-generated C into a PX4 module: [UNKNOWN].
- On the companion, each input arrives with bridge rate limits and DDS latency [G 3.1, 3.7].

## Options

A. Companion: ROS 2 node via Ogma with own template.
B. FMU: PX4 module with Copilot C99, subscribing to uORB.
C. Hybrid from the start.

## Decision

**A in phase 1**; B is future work (phase 2), conditioned on a new P0
about PX4 v1.17 module structure and the FMU CPU/memory budget.

Phase 1 rules:
1. Own Ogma template in `ros2_ws/src/guara_monitors/template/` with
   `rclcpp::SensorDataQoS()`-compatible (best-effort) QoS and `_v1` names [G 3.5, 3.6].
2. Each verdict publishes the `stamp` of the most recent input sample used, to
   measure `L2` (SPEC §4).
3. Monitors are classified `switch` (enter `M(k)`) or `log` (record only).
4. Copilot-generated C must not depend on dynamic allocation, preserving
   option B.

## Consequences

- (+) Fast iteration; reuses the documented Ogma flow.
- (+) Isolates phase 1 from firmware modifications.
- (−) Extra latency `L1+L3` and bridge dependency; monitors do not see
  data at uORB rate.
- (−) Does not inherit FMU isolation (SPEC §7 item 7).
- Criterion to open phase 2: p99 of `L1+L2+L3` (M7) preventing O-1 with
  operationally acceptable parameters.
