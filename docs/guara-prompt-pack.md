# Guará — Prompt Pack for Agent Execution

Open Runtime Assurance (ASTM F3269) for PX4 via ROS 2. Project rationale: `docs/PROPOSAL.md`.

## How to use

1. Put the **CLAUDE.md** block at the repository root. It is the agent's fixed memory.
2. Run the prompts **in order**: P0 → P1 → P2 (one per milestone) → P3 → P4 → P5 → P6 → P7.
3. Use **one session per milestone**. Clean context reduces accumulated hallucination.
4. Never skip **P0**. It forces the agent to read the real source code before writing anything.
5. **The paper text is yours.** Use agents for code, experiments and review. NFM prohibits generative
   AI for the paper narrative; check each venue's policy.

## Techniques applied

- **Grounding before generation.** Every API comes from `repo@commit:file:line`, never from model memory.
- **Spec-first.** SPEC.md and ADRs with testable acceptance criteria before any code.
- **Executable acceptance criteria.** Each AC has the command that verifies it.
- **Verification loop with a stop.** Build, test and SITL; at most 3 attempts, then report instead of insisting.
- **Role separation.** One agent builds; another reviews as a skeptical program committee.
- **Structured outputs.** Tables and JSON with a confidence field (HIGH / MEDIUM / UNKNOWN).
- **No numbers without provenance.** Every result comes from `metrics.json` aggregated by a versioned script.

## P0 — Grounding (no code)

```xml
<role>
Integration engineer. Your only task in this session is to verify facts in the
source code. You do not write product code.
</role>

<setup>
Clone into third_party/ and record commits in third_party/VERSIONS.md:
PX4-Autopilot, px4_msgs, px4-ros2-interface-lib, nasa/ogma, nasa/daidalus,
nasa/fret, Copilot.
</setup>

<questions>
1. Which px4-ros2-interface-lib API lets a ModeExecutor activate internal
   modes (Hold, RTL, Land)? What is the call sequence?
2. What does PX4 do when an external mode or executor stops responding?
   Which timeouts exist and where are they configured?
3. Which /fmu/out/* topics are exposed by default (dds_topics.yaml)?
   Is a traffic/transponder topic exposed? If not, what is needed?
4. What is the current format of Ogma's variable DB for the ros backend?
   Show a real minimal example from the repository.
5. DAIDALUS v2 C++ API: how to insert ownship and intruders, get time to
   loss of well-clear and bands, and load a DO-365B configuration.
6. Is CopilotVerifier available in the current Copilot version? How is it invoked?
</questions>

<output_format>
File GROUNDING.md with table:
| # | answer | evidence (repo@commit:file:line) | confidence |
Confidence ∈ {HIGH, MEDIUM, UNKNOWN}.
</output_format>

<rules>
- No evidence in the code or in the repository's own documentation: write UNKNOWN.
- Answering from memory or by analogy with older versions is forbidden.
- List at the end the UNKNOWN questions that block P1.
</rules>
```

## P2 — Milestone template (implementation loop)

```xml
<milestone id="M{N}">{title, e.g.: RTA arbiter as ModeExecutor}</milestone>

<inputs>
- docs/SPEC.md §{sections}
- Acceptance criteria: AC-{x}..AC-{y}
- GROUNDING.md (allowed APIs)
</inputs>

<process>
1. Write a plan of at most 10 steps and show it before acting.
2. For each AC, write a test that FAILS. Run it and show the failure.
3. Implement the minimum for the test to pass.
4. Verify:
   colcon build --symlink-install
   colcon test && colcon test-result --verbose
   ./scripts/sitl_run.sh --scenario {scenario} --seed 42 --headless
5. On failure: quote the relevant log excerpt and state the hypothesis BEFORE
   changing code. At most 3 attempts; then stop and report.
6. After each green step, make a granular commit per CLAUDE.md.
</process>

<constraints>
- Use only APIs present in GROUNDING.md. New API: stop and request a new P0.
- Do not change tests to make them pass without justifying it in the report.
</constraints>

<report>
| AC | status | command | output excerpt |
Open risks | technical debt | next steps
</report>
```

Suggested milestone sequence:

- **M2** — Copilot monitor via Ogma subscribing to /fmu/out/* topics (end-to-end proof).
- **M3** — RTA arbiter as ModeExecutor, switching to Hold.
- **M4** — Geofence predictor (time to violation) integrated into the arbiter.
- **M5** — DAIDALUS node (separate package) publishing time to loss of well-clear.
- **M6** — Hysteresis, dwell time and return policy.
- **M7** — Latency budget measurement (p50/p99).
- **M8–M12** — LLM/voice embodiment track, see `docs/research/LLM-EMBODIMENT.md` §8.

## P4 — Scenario generator and batch evaluation

```xml
<task>Implement a parametric scenario generator and a resumable batch runner.</task>

<scenario_space>
- Encounters: approach angle, relative speed, vertical separation,
  intruder type (agricultural aircraft, drone), intruder position noise.
- Geofence: concave polygons, constant wind and gusts, cruise speed.
- Degradations: injected DDS latency, packet loss, stale data.
</scenario_space>

<run_contract>
Each run writes results/{run_id}/:
- config.yaml (parameters + seed + commits)
- metrics.json
- PX4 .ulg log
</run_contract>

<metrics>
- loss of well-clear (configured DAIDALUS definition)
- geofence violation (yes/no, maximum depth)
- switches: true vs false (criterion defined in SPEC)
- latency detection → recovery mode active (p50, p99)
- mission completion rate
</metrics>

<statistics>
- Proportions with Wilson 95% CI.
- Paired comparison RTA on vs off (same seed).
- Additional baseline: PX4 default failsafe without Guará.
</statistics>

<rules>
- Parallelism limited to N containers (parameter); resumable execution.
- No number in a report that does not come from versioned scripts/aggregate.py.
</rules>
```

```xml
<rules>

- Target metric: violations with RTA on vs off, for k ∈ {0, 0.05, 0.2}.
```

## P6 — Skeptical reviewer (program committee)

```xml
<role>
Program committee member of the NASA Formal Methods Symposium.
Skeptical, expert in runtime verification and UAS certification.
</role>

<task>Review docs/SPEC.md, results/summary.md and docs/claims.md.</task>

<checklist>
1. Overclaiming: does any sentence suggest certification or an undemonstrated guarantee?
2. Threats to validity: SITL vs real, scenario bias, seeds, fair baseline.
3. What the arbiter does NOT guarantee: arbiter outside the FMU, stale data, spoofed sensors.
4. Is the comparison with PX4's default failsafe fair and reproducible?
5. Omitted related work: ICAROUS and FRET/Copilot monitoring on it,
   RTLola/Volocopter (CAV 2024), Platum/DATUM (MAVLink), SOTER on ROS,
   ASTM F3269, NASA RTA recommendations (Brat & Pai),
   LLM drone control (TypeFly, PX4+Ollama agents, MCP/MAVLink servers), RoboPAIR, RoboGuard.
6. Reproducibility: pinned commits, container, single reproduction script.
</checklist>

<output>
- Score 1–5 per item.
- The 5 most serious problems.
- For each problem, the experiment or change that would resolve it.
</output>
```
