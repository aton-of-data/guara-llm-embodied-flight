## Defect found and fixed (attempt 1 → 2)

- Log excerpt (run `20260911T165444Z_hover_s42`): `etc/init.d-posix/rcS: 198: bc: not found` / `ERROR [param] not enough arguments.` ×4.
- Hypothesis: rcS computes link-loss timeouts with `bc` when `PX4_SIM_SPEED_FACTOR` is set (A.22); image lacks `bc`.
- Fix: install `bc` in the image; the run contract now fails on any `ERROR [param]` or rcS `not found` line.
- Verified: `COM_DL_LOSS_T set to 10`, `COM_RC_LOSS_T set to 1.0`, `COM_OF_LOSS_T set to 1.0`, `COM_OBC_LOSS_T set to 5.0` in run `20260911T165638Z_hover_s42`.
- The first AC-2 PASS (before the fix) was a false pass; the contract was tightened accordingly.

Also observed: the XRCE agent log shows `session established` and PX4 created `/fmu/out/*` data writers
(e.g. `rt/fmu/out/arming_check_request_v1`), consistent with [G 3.1, 3.5].

## Open risks

- AC-2b compares only `config.yaml` (inputs), as SPEC defines. It does not show trajectory repeatability;
  PX4 noise seed is fixed and thread scheduling is uncontrolled (A.20). Proposed AC-2c for P4: bounded
  trajectory divergence between same-seed runs, metric from ULog via script.
- SIH dynamics fidelity vs Gazebo is unassessed; `a_brake`, `τ_rec` measured in SIH may differ.
- Runs are real-time (`PX4_SIM_SPEED_FACTOR=1`); a 1,000-encounter batch (RQ1) needs faster-than-real-time or parallel containers.

## Technical debt

- Single instance per container (UDP 8888, px4 instance 0); parallel runs need one container per run (P4 rule).
- Runner parses `listener` text output; replace with ROS 2 topic checks once `guara_rta` exists (M3).
- Image is not multi-stage; size not optimized.
- `guara_dirty` is computed on host; runs started inside an already-running container inherit the value at container start.
